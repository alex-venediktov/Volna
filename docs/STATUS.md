Урок для новых скиллов: в `description` держать только зону и триггер вызова («вызывать ПЕРЕД
…»), перечисление правил — в теле. Полный список запретов в описании стоил вдвое дороже и

скиллов, сопоставление по зонам (а не по именам) и вердикт на каждое пересечение —
полный дубль / дубль с деталями / конфликт правил / своя зона.

### Принятые решения (вход для следующих волн)
1. **Журналы не коммитятся** — в `.gitignore` рабочего репозитория: `.volna/state.json`,
   `.volna/journal/`, `.volna/project.local.md`. Шарятся `.volna/knowledge/` и `.volna/project.md`.
2. **Сначала под один проект**, без слоёв абстракции: этапы написаны прямо под delphi-порт
   и TFS. Нейтральность извлекать после задачи в другом проекте.
3. **Правила этапов — черновик** (обкатаны ~на 5 задачах с разным успехом), менять
   разрешено; `required` оставлен только для необратимого (`intake`, `commit`, `push-pr`,
   `close`), остальное `expected`/`optional`; ревизия правил — часть этапа `capture`.
4. **Конфликт про коммиты**: правило проекта запрещает трейлеры, включая `Co-Authored-By`.
   Прописано в `stages/commit.md` как переопределение общего поведения.
5. **Порядок TFS для бага**: задача-фикс создаётся на `push-pr` **до** push (иначе в PR попадёт
   номер бага); статусы меняются только на `close`, каждое изменение — отдельным подтверждением;
   ветка «изменений кода нет» — полноценный путь без PR и без пустого коммита.
6. **Усиление против прежней версии флоу**: для багфикса требуется тест, который падал бы до правки, либо
   объяснение, почему такой невозможен.
7. **Никаких внешних зависимостей от других репозиториев.** Что было нужно — перенесено сюда
   (клиент трекера, знание об API, тексты правил). Проект ставится и работает сам по себе.
8. **Публичный репозиторий = только процессная часть.** Имена внутренних систем, адреса и пути
   в него не попадают: приватное — в `.env` рабочего репозитория, предметные скиллы — там же
   (`docs/PROJECT-SKILLS.md`). Этап зовёт проектный скилл, если он есть, иначе работает по
   конвенциям из `.volna/project.md`.
9. **Установка — штатным плагином, а не своим CLI.** Отдельный бутстрап-CLI (как у
   spec-kit на `uv`) не нужен: он оправдан мультиагентностью, а у нас один агент. Свой код в
   установке — только `install.ps1` на PowerShell 5.1 для тех, кому нужна одна команда.

## Что осталось

### Следующий шаг — проверка W1 на живой задаче (блокирует W2)
От пользователя нужно:
1. Опубликовать репозиторий на GitHub (`alex-venediktov/Volna`) — установка настроена на него.
2. Поставить плагин (`/plugin marketplace add alex-venediktov/Volna`, `/plugin install volna@volna`)
   либо подключить junction'ами для локальной разработки — `docs/INSTALL.md`.
3. В рабочем репозитории: `/volna:init`, заполнить `.env` и `.volna/project.md`,
   проверить `/volna:doctor`.
4. Пройти одну реальную задачу командами `/volna:*`.

Что ловить на прогоне: не многословны ли `stages/*.md`; не мешает ли гейт чистого дерева;
хватает ли семи подпунктов журнала или сократить; какие этапы систематически пропускаются
(сигнал упростить флоу, а не ужесточать).

Плюс `commands/recall.md`.
Индекс журналов в KB-сервере (`search_journal`) — **отложен до 20–30 журналов** (решение D-F);
второй MCP-сервер не поднимать (V6).
