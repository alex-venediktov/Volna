# Исследование: локальный трекер через команды MCP-сервера

> **Дата:** 11.10.2026. **Проверено на:** живом сервере `task-tracker` (Streamable HTTP,
> `http://<хост>:8113/mcp`), запросами только на чтение. Задача - `261011-mcp-local-tracker`.

## Вердикт

**Можно, и без риска для установок, где сервера нет.** Трекер в «Волне» уже вынесен на одну ось:
строка профиля `трекер` -> файлы `skills/volna-flow/trackers/<трекер>/<этап>.md` -> CLI трекера.
Проект с другим значением строки файлов нового трекера не открывает, переменных его не заводит и
в контексте за него не платит - так устроена поддержка Jira (решение 54 в
[`../DECISIONS.md`](../DECISIONS.md)). Новый трекер - третье значение той же строки.

Условия, без которых «не нарушить» не выполняется:

1. **плагин сервер не объявляет** (`mcpServers` в манифесте не появляется): объявленный сервер
   подключается в каждой сессии каждой установки, а без сети с ним висит в списке как
   «failed to connect»;
2. **недоступный сервер - останов с причиной, а не тихий переход в локальный режим** (запись вики
   `flow-profile-placeholder`: неверное разрешение не обнаруживается никогда);
3. **ход к серверу ограничен таймаутом**: адрес в сети, где хоста нет, не отвечает отказом -
   соединение висит (замер на свободном адресе той же сети: `curl --max-time 3` ->
   `000 Connection timed out`); быстрый отказ бывает только без сети вовсе.

## Что показал сервер

| Свойство | Наблюдение | Что значит для «Волны» |
|---|---|---|
| транспорт | `initialize` не отдаёт `Mcp-Session-Id`; `tools/list` и `tools/call` проходят отдельными POST | команды сервера доступны Node без зависимостей: `fetch` + JSON-RPC, тест - на подставном `fetch` |
| инструменты | `list_projects` `list_tasks` `get_task` `create_task` `update_task` `move_task` `comment_task` | хватает на `intake`, `plan`, `deliver`, `close`, `split` |
| проект | заголовок `X-Project`; чужой проект - аргумент `project` | имя проекта - командная настройка, а не машинная |
| статусы | `backlog` `todo` `doing` `review` `done`, набор постоянный | `plan` -> `doing`, `close` -> `review` либо `done` |
| ответ | `structuredContent.result` и тот же JSON строкой в `content[].text` | клиент читает `structuredContent` |
| ошибка инструмента | `isError: true`, текст `задачи #999999 нет`; HTTP при этом 200 | ошибку различает клиент по полю, а не по коду HTTP |
| текст задачи | `get_task(markdown=true)` либо `GET /t/<id>.md` (404 на отсутствующую) | постановка - markdown без конвертера |
| удаление | нет: ненужную задачу переводят в `done` с комментарием | отменённый ребёнок на `split` закрывается так же |
| секрет | нет: доступ ограничен локальной сетью | в `.env` только адрес; правило о файле с токеном не задействовано |

## Чего у сервера нет, а флоу ждёт

- **id - короткие числа** (`1`, `2`) или свои (`new_id`: латиница, цифры, `-`, `_`). Форма «число
  4-6 цифр» их не берёт в трёх местах: таблица входа `/volna:task` и `stages/intake.md`,
  `TRACKER_ID` в `bin/volna-task.mjs:32`, `mentionedTask()` в `hooks/preamble.mjs:137`. Для шапки
  голое `1` в тексте сообщения неотличимо от любого числа, поэтому упоминание номера там узнавать
  не стоит вовсе;
- **типа задачи нет** - есть теги (`bug`, ...). Вид для флоу берётся из тега, без тега - `task`;
- **родителя и связей нет**. Дети на `split` заводятся `create_task`, ссылка на родителя - строкой
  в постановке и комментарием `comment_task` у родителя; очередь по-прежнему держит журнал «Волны»
  (`children`);
- **часов, оценки и исполнителя нет**. Часы и итог на `close` - в журнал, как в ветви Г; в трекер
  уходят статус и комментарий;
- **задачи-фикса и PR нет** - `deliver` пишет хеш коммита комментарием, как у Jira.

## Два пути к командам сервера

| | **А. Инструменты MCP у модели** | **Б. CLI плагина - клиент того же MCP** |
|---|---|---|
| свой код | нет | клиент, CLI и тест, по образцу `lib/jira-client.mjs` |
| имя команд | `mcp__<имя>__get_task`: имя даёт человек в `claude mcp add`, в тексте плагина его не зашить | постоянное: `volna-tt get <id>` |
| проверка | только на живом сервере | подставной `fetch`, без сети |
| таймаут | у Claude Code, вне плагина | `AbortSignal.timeout` в клиенте |
| `doctor` | видит, подключены ли инструменты | вызывает `initialize` и называет причину отказа |
| машина без сервера | инструментов нет, модель узнаёт это по их отсутствию | CLI отвечает «сервер недоступен» за секунды |

**Рекомендация - Б.** Доводы решения 54 против MCP Atlassian («хуки, `doctor` и headless-запуски
MCP звать не могут, подставным клиентом он не тестируется») относятся к пути А и здесь остаются в
силе. Путь Б их снимает, не отказываясь от команд сервера: CLI зовёт те же `get_task` и
`move_task`, только сам, по HTTP. Подключение сервера к Claude Code остаётся ручным удобством
человека (`claude mcp add -s local ...`), флоу на нём не держится.

## Универсальный адаптер вместо третьего CLI

У двух CLI набор глаголов уже почти общий - его никто не проектировал, он сложился:

| Глагол | `volna-tfs` | `volna-jira` | `task-tracker` |
|---|---|---|---|
| `check`, `get`, `comment`, `describe` | есть | есть | `initialize`, `get_task`, `comment_task`, `update_task` (поле заменяется целиком: дописать - через `get_task`) |
| `query` / список своих | WIQL | JQL | `list_tasks` по статусу и тегу |
| `state` | запись поля (`Active`, `Resolved`) | переход процесса, имена свои у проекта | `move_task`, пять постоянных статусов |
| `create --parent` | связь parent | поле parent | нет связи: строка в постановке |
| `time`, `estimate` | есть | есть | нет |
| PR, задача-фикс, поля процесса, вложения | есть | нет | нет |

Отсюда форма адаптера: **один CLI `volna-tracker <глагол>`, шлюз выбирается строкой профиля**,
шлюзы - существующие `lib/tfs-client.mjs`, `lib/jira-client.mjs` и новый клиент `task-tracker`.
Контракт - общие глаголы плюс две вещи, без которых он не сходится:

- **статусы по смыслу** (`в работе`, `на проверке`, `закрыта`), а имя в трекере - строкой
  `.volna/project.md`: у Jira оно своё у каждого проекта, у TFS зависит от процесса;
- **`capabilities`** - что шлюз умеет (`time`, `estimate`, `parent`, `pr`). Чего шлюз не умеет,
  того этап не делает молча - тот же принцип, что у профиля (запись вики `flow-profile-absent-step`).

Что это даёт: тексты этапов зовут одну команду. `trackers/<трекер>/plan.md` у TFS и Jira - это
одна команда `state` с разным именем статуса и правило Jira о недоступном переходе; с контрактом
от файла остаётся это правило. `intake.md` сводится к `get` плюс особенности ответа (у Jira - вид
задачи для флоу и родитель в чужом проекте).
Следующий трекер - шлюз и проверки контракта, без новых текстов этапов. В файлах трекера остаётся
то, что в контракт не ложится: задача-фикс и PR у TFS, недоступный переход у Jira.

Чего это не меняет: машины и установки без трекера - строка `трекер: нет` до адаптера не доходит,
условия раздела «Вердикт» те же.

Порядок, при котором не ломается работающее:

1. контракт и `volna-tracker` поверх клиентов как они есть; `volna-tfs` и `volna-jira` остаются
   рабочими командами - на них ссылаются `.volna/project.md` проектов;
2. шлюз `task-tracker` пишется сразу под контракт: три реализации проверяют контракт, а не одна;
3. тексты этапов переводятся на контракт по одному: `plan` и `intake` (проще всего), затем
   `split`, `deliver`, `close`.

**Обобщённый шлюз «любой трекер с MCP»** (таблица «глагол -> инструмент и аргументы» в профиле):
сойдётся для серверов вроде этого - без сессии и без авторизации. Сервер с OAuth или сессией
голым `fetch` не обслужить, а соответствие аргументов и разбор ответа всё равно пишутся под
каждый сервер. Поэтому шлюз `task-tracker` - код с тестом, а не таблица.

## Где сервера нет

**(а) Другие установки плагина.** Профиль у них `нет`, `tfs` или `jira` - файлы
`trackers/task-tracker/` не открываются, `init` и `doctor` блок `TT_*` не пишут и не проверяют,
CLI не вызывается. Изменений в поведении и в стоимости контекста нет. Код, который ветвится по
трекеру, - один `hasTracker()`, и его проверки в `hooks/test-hooks.mjs` (`нет`, профиля нет,
плейсхолдер) новое значение не задевает: оно отвечает «трекер есть», как `tfs` и `jira`.

**(б) Тот же проект на машине без доступа к серверу.** Профиль коммитится, значит строка
`трекер: task-tracker` действует и там. Журналы не коммитятся (решение 1), поэтому задача трекера
с одной машины на другую не переезжает - остаются отдельные вызовы к серверу:

| Место | Поведение без сервера |
|---|---|
| `intake` с номером | CLI: «сервер `<адрес>` недоступен» -> останов; человеку - вести задачу локально текстом или вернуться к ней из сети |
| `intake` с текстом, файлом, ссылкой | без изменений: `mode: local`, сервер не нужен |
| `plan` | статус не поставлен -> строка в `open[]`, работа идёт дальше: статус обратим и ставится на `close` |
| `deliver`, `close`, `split` | `required`: останов с причиной, решение человека |
| `doctor` | красная строка «`TT_MCP_URL` не отвечает» - отдельно от «переменной нет» |
| hooks | с трекером не говорят; гейт push держится на `hasTracker()`, а он для нового значения отвечает «трекер есть» - верно |
| подключение MCP | `-s local` на своей машине; `-s project` кладёт сервер в `.mcp.json` репозитория, и каждая машина без сети видит «failed to connect» |

## Что менять при реализации

| Файл | Правка |
|---|---|
| `lib/tt-client.mjs`, `bin/volna-tt.mjs`, `bin/test-volna-tt.mjs` | клиент JSON-RPC `tools/call` с `X-Project` и таймаутом; команды `get`, `list`, `state`, `comment`, `create`; тест на подставном `fetch` |
| `skills/volna-flow/trackers/task-tracker/{intake,plan,deliver,close,split}.md` | пять файлов по образцу `trackers/jira/` |
| `skills/volna-flow/templates/project.template.md` | значение в строке `трекер`, блок «При `трекер: task-tracker`»: проект (`X-Project`), статусы закрытия |
| `commands/init.md`, `commands/doctor.md` | блок `.env` (`TT_MCP_URL`, `TT_PROJECT`), проверка `initialize` |
| `commands/task.md`, `stages/intake.md`, `bin/volna-task.mjs` | номер 1-6 цифр - id трекера при этом профиле |
| `docs/reference/task-tracker-mcp.md` | подвохи: ошибка в `isError` при HTTP 200, `structuredContent`, висящее соединение |
| `CLAUDE.md`, `.volna/project.md` | седьмой набор тестов в списке команд |

Объём - того же порядка, что поддержка Jira: клиент, CLI, тест и пять файлов трекера; тексты этапов
меняются только в таблице входа `intake`.

С адаптером (раздел «Универсальный адаптер») вместо `bin/volna-tt.mjs` - `bin/volna-tracker.mjs`
и проверки контракта на трёх шлюзах; файлы `trackers/task-tracker/` нужны только под то, что в
контракт не легло, а `plan.md` и `intake.md` прежних трекеров сводятся к контракту отдельным шагом.

## Отвергнуто

- **Сервер в манифесте плагина** - подключается во всех установках, нарушает условие (а).
- **Определять трекер по доступности сервера** («отвечает - трекер, нет - локально»): на машине
  без сети номер задачи молча станет локальным id, причину человек не найдёт.
- **Переопределение профиля на машине** (`project.local.md`): профиль описывает проект, а не
  машину; машинное в нём - только адрес, и он уже в `.env`.
- **Путь А как единственный**: имя инструментов зависит от человека, проверка - только вживую,
  таймаут вне плагина.

## Открытые вопросы к реализации

1. Форма: третий CLI по образцу Jira либо адаптер `volna-tracker` с шлюзом `task-tracker` первым
   под контракт.
2. Значение строки профиля: `task-tracker` (имя сервера) или короче.
3. Номер задачи в шапке: не узнавать вовсе либо узнавать только в форме `#12`.
4. Статус закрытия: `review` (проверит человек) или `done`.
