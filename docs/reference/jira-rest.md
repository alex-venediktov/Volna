# Подвохи REST API Jira Cloud

Что стоило времени при написании `lib/jira-client.mjs`. Проверено на `<компания>.atlassian.net`
(проект `ABC`, classic) в августе 2026.

## Версия API: v2, а не v3

В v3 текстовые поля (`description`, тело комментария) - документ **ADF**: вложенный JSON
(`{type: "doc", version: 1, content: [...]}`). В v2 те же поля - **строка wiki-разметки**.
Вход «Волны» всегда markdown, поэтому взят v2: нужен один конвертер разметки, а не генератор
и разборщик дерева.

v2 не выведен из обращения: v3 - это ADF-двойник v2, а не его замена. Смена версии - одна
константа в пути запроса, эндпоинты те же.

Проверить, что отдаёт конкретный экземпляр:

```
curl -u "<почта>:<токен>" ".../rest/api/2/issue/<ключ>?fields=description"
```

Пустое описание приходит как `null`, и проверка типа значения в JavaScript тогда врёт
(`typeof null === "object"`): смотреть надо задачу с непустым описанием.

Отрисованный HTML вместо разметки: `?expand=renderedFields`, поле `renderedFields.description`.

## Поиск: прежний адрес удалён

`GET|POST /rest/api/{2,3}/search` отвечает **410 Gone**. Работает `/rest/api/2/search/jql`, и он
устроен иначе:

- **список полей обязателен** - `fields=summary,status,...`. Неявного «отдай всё» больше нет;
- **пагинация курсорная**: ответ содержит `nextPageToken` и `isLast`, а `startAt` и `total` -
  **нет**. «Сколько всего нашлось» - отдельный запрос `/search/approximate-count`;
- сервер иногда отдаёт непустой `nextPageToken` бесконечно. Цикл обязан иметь **предел числа
  страниц**, иначе он не заканчивается. Клиент отдаёт признак `truncated`, и команда `query`
  говорит человеку, что ответ обрезан.

## Отсутствие доступа маскируется под ответ по существу

Честно отвечает **только** `/myself`. Остальные читающие адреса на запрос без прав отдают то, что
читается как факт:

| Запрос | Ответ без доступа | Как читается |
|---|---|---|
| `/myself` | 401 «Client must be authenticated» | отказ |
| `/search/jql` | **200** `{"issues":[],"isLast":true}` | «задач нет» |
| `/issue/<ключ>` и его подресурсы | **404** «Issue does not exist or you do not have permission to see it» | «неверный ключ» |
| `/project/<ключ>`, `/project/<ключ>/statuses` | **404** «No project could be found with key» | «неверный проект» |

Пустой список приходит и на запрос **вовсе без заголовка авторизации**: поиск обрабатывает такой
запрос как анонимный, а не как неаутентифицированный. Признак того же: сообщения об ошибке
возвращаются на языке анонима (наблюдался китайский), а не на языке учётной записи.

Права проверяются **после** синтаксиса: битый JQL честно даёт 400 даже с неверным токеном, и по
этому ответу о доступе судить нельзя.

Отсюда правило клиента: **отрицательный ответ на чтение фактом не является, пока не проверен
доступ**. Проверка — тот же `/myself` (`accessProblem()`), и зовётся она только на отрицательном
ответе: пустая выборка или 404. Плата за неё нулевая, потому что случай редкий.

## Статус меняется переходом, а не записью поля

Записать `fields.status` нельзя. Порядок: прочитать доступные переходы
(`GET /issue/{key}/transitions`), выбрать нужный, выполнить по **id**
(`POST /issue/{key}/transitions`).

- **имя перехода не совпадает с именем статуса**: `В тестирование` ведёт в статус `Тестирование`,
  `Пауза` - в `On hold`, `Cancelled` - в `Отменено`. Сопоставлять надо и по имени перехода, и по
  имени целевого статуса;
- набор переходов зависит от текущего статуса и от прав: «поставить В работе» из текущего
  состояния может быть недоступно вовсе. Это не сбой - это рабочий процесс, и человеку надо
  показать список доступных переходов;
- имена статусов в одном проекте бывают на разных языках: `Backlog`, `selected for development`,
  `В работе`, `Dev Test`, `For testing`, `Тестирование`, `AN ACCEPTANCE`, `Ready to prod`,
  `Готово`, `On hold`, `Отменено`.

## Имя типа задачи зависит от эндпоинта

Одно и то же поле приходит по-разному:

| Запрос | Что отдаёт |
|---|---|
| `GET /project/{key}` | `Задача, Подзадача, История, Баг, Баг (подзадача), Эпик` |
| `GET /project/{key}/statuses` | `Task, Sub-task, Story, Bug, bug, Epic` |
| `GET /issue/{key}` | имя типа под язык учётной записи токена |

Системные типы переводятся под язык пользователя, и **ветвление по строке имени ломается**.
Опора - `issuetype.id` и признак `subtask`; для показа человеку берётся имя как пришло.
В клиенте это `issueKind()`: словарь на оба написания сразу.

## Родитель бывает в чужом проекте

`ABC-2228` -> родитель `XYZ-4475`. `JIRA_PROJECT` ограничивает выборки и создание, но чтение
по ключу работает через границу проекта. Постановка часто лежит именно в родителе.

## Аутентификация

Basic от строки `<email>:<api_token>` в base64. Отличия от TFS: логин не пустой, и без правильной
почты токен бесполезен (ответ 401). Токен выпускается в профиле Atlassian (Account settings ->
Security -> API tokens), хранится в файле, путь к файлу - в `JIRA_TOKEN_FILE`. BOM (utf-8-sig)
и края при чтении срезаются, значение не логируется.

## Ограничение частоты

При 429 сервер присылает `Retry-After` - секунды либо дату. Клиент обязан выждать названное время;
пауза сверху ограничена, чтобы одиночная команда не висела вечно.

## Учёт времени

- списание - `POST /issue/{key}/worklog` с `timeSpentSeconds`; прибавляется к затраченному и на
  столько же уменьшает остаток;
- оценка и остаток - поле `fields.timetracking` (`originalEstimate`, `remainingEstimate`) в
  `PUT /issue/{key}`;
- запись длительности («1d», «2h 30m») зависит от настроек экземпляра:
  `GET /rest/api/2/configuration` отдаёт `workingHoursPerDay` (у нас 8) и `defaultUnit` (час).
  Часы надёжнее дней: день в разных проектах разной длины;
- порядок на закрытии: **часы и остаток до смены статуса**. Правило перехода может запретить
  трогать время после закрытия.

## Чего клиент пока не умеет

Создание задач (`createmeta` и обязательные `customfield_NNNNN`), связи между задачами, метки,
вложения. Задача-фикс на `deliver` в Jira не создаётся, pull request живёт вне Jira (Bitbucket).
