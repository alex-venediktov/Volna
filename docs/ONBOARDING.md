# Первая задача с «Волной» за 10 минут

> Для того, кто ставит «Волну» впервые. Ничего знать заранее не нужно: установка — 5 минут,
> дальше сразу боевая задача. Подробности установки — [`INSTALL.md`](INSTALL.md),
> устройство и команды — [`../README.md`](../README.md).

| Шаг | Что делаете | Время |
|---|---|---|
| 1 | ставите плагин | 2 мин |
| 2 | разворачиваете проектную часть, заполняете `.env` | 3 мин |
| 3 | `/volna:doctor` — проверка | 1 мин |
| 4 | `/volna:task <номер>` — задача в работе | 1 мин |
| 5 | работаете; «Волна» ведёт журнал и подсказывает следующий этап | остальное |

---

## Что понадобится

- **Claude Code** (CLI, десктоп или IDE-расширение) — «Волна» живёт внутри сессии;
- **Node.js** — для hooks и CLI над трекером; проверить: `node --version`;
- **доступ к трекеру** и персональный токен (PAT), сохранённый **в отдельном файле** —
  в `.env` пойдёт путь к этому файлу, а не сам токен. Нужны только если задачи приходят
  из трекера: проект может работать и без него (профиль `трекер: нет`);
- рабочий репозиторий, в котором будете вести задачи.

## Шаг 1. Плагин (2 мин)

В сессии Claude Code:

```
/plugin marketplace add alex-venediktov/Volna
/plugin install volna@volna          # процесс: флоу, журнал, команды
/plugin install volna-craft@volna    # ремесленные правила — по желанию
```

Второй плагин необязателен: без него флоу работает, просто без правил порта, стиля коммитов
и тестов. Цена обоих в контексте — [`COST.md`](COST.md).

Если у команды это уже прописано в `.claude/settings.json` рабочего репозитория, плагин
включится сам при запуске Claude Code — тогда шаг пропускается.

## Шаг 2. Проектная часть (3 мин)

В корне рабочего репозитория, в сессии:

```
/volna:init
```

Появятся `.volna/` (настройки, журналы, знания), `.env` из шаблона и правила в `.gitignore`.
Команда ничего не перезаписывает и спрашивает только то, что нельзя угадать.

Первым делом команда спросит **профиль проекта**: один репозиторий или несколько, есть ли трекер,
чем кончается доставка (коммит, push, PR), есть ли эталонная реализация. Ответы ложатся в секцию
`## Профиль` файла `.volna/project.md` и решают, какие шаги в этом проекте вообще существуют:
без трекера никто не спросит номер задачи и не пойдёт двигать статусы.

**Продуктовая команда с трекером и несколькими репозиториями** отвечает так:

```
- репозитории: несколько
- трекер: tfs
- приём задач: номер
- доставка: commit+push+pr
- закрытие: трекер
- эталон: delphi
```

Это полный флоу, каким «Волна» была до появления профиля: задача по номеру из TFS, задача-фикс
и PR на `deliver`, статусы и часы на `close`, сверка с эталоном. **Свой репозиторий без
трекера** — противоположный набор: `один · нет · текст · commit+push · журнал · нет`.

Ставили не командой, а `install.ps1`? Тогда в `project.md` лежит шаблон с плейсхолдерами
(`трекер: <нет|tfs>`), и профиль надо заполнить руками или прогнать `/volna:init` — пока
плейсхолдеры на месте, первая же задача остановится и спросит.

Дальше руками:

1. **`.volna/project.md`** — команды сборки и тестов, конвенция ветвления, правила коммитов.
   Плейсхолдеры `<заполнить>` — это и есть список того, что нужно от вас.
2. **`.env`** — только то, что просит профиль: целевая ветка, а при трекере — его адрес, проект
   и **путь к файлу с PAT**. Токен внутрь `.env` не вписывать: там только путь к файлу с ним.

Проверьте, что `.env` попал в `.gitignore` (`/volna:init` это делает, `/volna:doctor` проверит).

## Шаг 3. Проверка (1 мин)

```
/volna:doctor
```

Проверит файлы и переменные (те, которых требует профиль), гигиену секретов, доступ к трекеру
(`volna-tfs check`), доступность базы знаний и совпадение активной задачи с текущей веткой.
То, чего в профиле нет, помечается «не требуется в этом профиле», а не красным. Красное чините
до первой задачи — на этапе `close` неверный `.env` остановит работу в самый неудобный момент.

## Шаг 4. Берём задачу (1 мин)

```
/volna:task 21571
```

Что произойдёт: проверка, что нет другой активной задачи → чтение постановки из трекера (тип,
описание, обсуждение, связи, вложения) → карточка задачи и знания команды по её теме → журнал
из двух файлов (`.volna/journal/TASK-21571.md` — состояние задачи,
`.volna/journal/logs/TASK-21571.log.md` — лог итераций) → чек-лист этапов в UI сессии. Ветка по
конвенции проекта и статус `Active` в трекере появляются дальше: статус — на `plan`, ветка — на
`implement`.

Задачи в трекере нет (исследование, разбор) — вместо номера дайте текст или путь к `.md`:
`/volna:task разобраться, почему вложения приходят с битым именем`. Флоу и журнал те же, id
собирается из даты и ключевых слов.

С этого момента в шапке каждого сообщения видно: номер задачи, этап `k/13`, до трёх открытых
пунктов и напоминание, если журнал давно не дописан.

## Шаг 5. Как идёт работа

Флоу — 13 этапов, **предпочтительный порядок, а не рельсы**:

`intake` → `analyze` → `spec` → `plan` → `implement`×N → `advocate` → `fixtures` →
`unit-tests` → `visual` → `capture` → `deliver` → `close` → `cleanup`

Первые девять — от приёма задачи до визуальной сверки — идут **сами, одной цепочкой**: пока
продолжение единственное, «Волна» не ждёт команды, а сообщает «этап `X` закрыт → иду в `Y`» и
работает дальше. Вас она спросит там, где иначе нельзя: развилка, расхождение с эталоном, нужен
ваш вердикт или доступ, и перед доставкой. Цикл `implement → advocate` тоже крутится сам: находка
адвоката и красный тест — это правка, а не вопрос.

**У каждого этапа своя команда — имя этапа с префиксом:** `/volna:analyze`, `/volna:implement`,
`/volna:deliver`. Набрать `/volna:` и выбрать из списка — вспоминать имена не нужно. Первый этап
`intake` вызывается как `/volna:task <номер>`, остальные — по своему имени. Команды нужны, чтобы
вернуться назад, начать новую итерацию или войти в доставку — вперёд по цепочке «Волна» идёт сама.

Всё, что нужно знать в первый день:

- **«что дальше?»** — обычный вопрос в чат, «Волна» ответит по карте этапов; ход, которым работа
  отдаётся вам, к тому же кончается готовой командой следующего шага **без параметров** — её можно
  принять нажатием `Tab` (команду с пробелом внутри подсказка у поля ввода не показывает, поэтому
  в этой строке аргументов не бывает);
- **`/volna:status`** — где мы: этап, карта этапов, пройденное, пропущенное, открытые вопросы;
- **этап не нужен** — просто вызовите команду следующего: причина пропуска уйдёт в журнал при
  переходе. Это нормальный путь, а не нарушение. Есть и `/volna:skip <этап> <причина>`, если
  причину хочется задать своими словами;
- **повторный вызов пройденного этапа** (`/volna:implement`) — это новая итерация: прошлые записи
  журнала не переписываются, добавляется новая. Причину возврата «Волна» берёт из разговора;
- **`/volna:recall <тема>`** — что команда уже знает по теме (записи опыта и прошлые журналы);
  пустой ответ — законный результат;
- **`/volna:checkpoint`** — перед `/compact`: дописать лог этапа и **переписать секцию
  `## Состояние`** — резюме, по которому работа продолжается с нуля. Перезапускать процесс
  не нужно — это дороже.

В журнале две части: наверху `## Состояние` — картина задачи сейчас, она переписывается; ниже
секции этапов — append-only история итераций. Возвращаясь к задаче, читайте «Состояние», а не
лог: на живой задаче он вырастает до сотен строк, и ранние выводы там бывают уже отменёнными.

Задача ведётся **в одном контексте**: не начинайте вторую параллельно, «Волна» на это
не рассчитана и предупредит.

Уходите от машины, а агент может спросить? Вопрос и запрос разрешения забираются на телефон
через Remote Control — как включить и что при этом уходит наружу, в [`REMOTE.md`](REMOTE.md).

## Шаг 6. Доставка и закрытие

Перед доставкой — `/volna:capture`: опыт задачи превращается в записи `.volna/wiki/`, замечания
о самой «Волне» уходят в `.volna/feedback.md`. Этап стоит здесь затем, чтобы знание уехало **тем же
коммитом**, что и работа: `.volna/wiki/` коммитится, и записанное после доставки потребовало бы
второго коммита, а чаще не записывалось бы вовсе.

`deliver` и `close` — необратимые действия, они требуют явного «да» от вас. Коммит отдельным
этапом не идёт: он первый шаг `deliver`, и «да» вы даёте один раз на всю доставку — коммит,
задача-фикс, push, PR. Автопроход здесь кончается: в доставку «Волна» сама не входит.

**Гейт на commit может отказать** — это штатное поведение, а не поломка:

| Отказ | Почему | Что сделать |
|---|---|---|
| «нет записи журнала по текущему этапу» | коммит без следа в журнале | `/volna:journal <что сделано>` и повторить |
| «не начат этап `deliver`» при push | пушим то, чего нет в флоу | вызвать `/volna:deliver` или объяснить причину через `/volna:skip` |
| предупреждение про `fix_task` у бага | для бага не создана задача-фикс | создать её на `deliver` **до** push, иначе в PR попадёт номер бага |

`/volna:off` глушит подсказки и шапку, но **не гейт**: он защищает необратимое.

Закрытие — `/volna:close`: статусы в трекере, списание времени, маршрут тестеру. Каждое
изменение в трекере — отдельное подтверждение, ничего не уходит молча.

Дальше последний этап `/volna:cleanup`: обновить затронутые репозитории, удалить слитые локальные
ветки (ветку задачи — только после слияния PR), переиндексировать базу знаний, убрать временные
снимки, назвать итог задачи, снять её из активных и предложить начать следующую с `/clear`. Уборка
нужна и там, где закрытия в трекере не было: задача брошена или разобрана без правок кода.

Опыт к этому моменту уже вынесен: `/volna:capture` стоит **перед доставкой**, чтобы записи
`.volna/wiki/` уехали тем же коммитом, что и сама работа.

У `capture` два выхода, и путать их не надо: **знание о продукте** (эталон, инфраструктура, грабли)
идёт в `.volna/knowledge/` и остаётся в проекте, а **замечание о самой «Волне»** — этап мешал,
правило оказалось неверным, шаг всё время пропускался — в `.volna/feedback.md`. Второй файл
локальный и разбирается при выпуске версии плагина: если сказать о замечании только в чате, до
правки правил оно не доживёт. Накопилось больше пяти открытых пунктов — `/volna:doctor` напомнит,
что их пора разобрать.

## Если что-то пошло не так

| Симптом | Причина | Решение |
|---|---|---|
| команд `/volna:*` нет | плагин не установлен или не включён | `/plugin` → проверить `volna@volna` |
| шапки задачи не видно | нет активной задачи, включён `/volna:off` или нет журнала | `/volna:status`, `/volna:on` |
| `doctor` ругается на доступ к трекеру | неверный адрес, проект или путь к PAT в `.env` | поправить `.env`, повторить `doctor` |
| запись в трекер ушла раньше, чем ожидали | флага подтверждения у CLI больше нет | смотреть заранее: тот же вызов с `--dry-run` печатает намерение и ничего не отправляет |
| ошибка «нет прав» при смене статуса | правило перехода требует заполненного поля (TF401320) | заполнить поле в трекере, повторить |
| ощущение, что правило мешает | правила — рабочий черновик | скажите об этом: на `capture` замечание уйдёт в `.volna/feedback.md` и попадёт в следующую версию плагина, обходить молча не надо |

## Что коммитится, а что нет

| Файл | Коммитится |
|---|---|
| `.volna/project.md`, `.volna/knowledge/**` | **да** — это общее знание команды |
| `.volna/journal/**`, `.volna/state.json`, `.volna/feedback.md`, `.env` | **нет** |

Если журнал или `.env` попали в индекс — сработала не та настройка `.gitignore`;
`/volna:doctor` показывает это отдельной строкой.
