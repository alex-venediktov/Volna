# Промпт-пакет: «Волна» — ведение задачи в одной сессии Claude Code

> **Волна** — лёгкое сопровождение одной задачи внутри Claude Code.
> Не оркестратор. Не внешний UI. Не мульти-сессия. Одна задача — один контекст — один UI
> (сам Claude Code), мягкий навигируемый флоу, накопительный журнал работ и расшаривание
> процесса внутри команды.
>
> Этот документ — **управляющий артефакт**, а не реализация. Он (1) причёсывает требования,
> (2) фиксирует противоречия и решения по ним, (3) даёт вердикт по реализуемости и
> рекомендованную архитектуру, (4) содержит **набор промптов** для пошаговой реализации.
>
> Как пользоваться: прогонять промпты Части 5 по волнам W0→W4. Части 0–4 передаются моделью
> как контекст (или держатся в репозитории и подключаются ссылкой на этот файл).

---

## Часть 0. Позиционирование: почему не внешний оркестратор

Альтернативный подход — внешний процесс-оркестратор, который сам гоняет headless-сессии по
графу этапов. Он был спроектирован и частично реализован; «Волна» — сознательный отказ от него
в пользу дешёвого и простого варианта. Сравнение осей:

| Ось | Внешний оркестратор | Волна |
|---|---|---|
| Кто ведёт процесс | оркестратор-процесс | **разработчик** + мягкие подсказки |
| Сессии | много, перезапускаемые headless | **одна интерактивная** |
| UI | свой web-UI | **штатный UI Claude Code** |
| Изоляция кода | git-worktree на задачу | **обычная ветка в рабочем дереве** |
| Флоу | граф с guardrails, принудительный | **чек-лист этапов, предпочтительный** |
| Параллелизм | много задач сразу | **одна задача за раз** |
| Своего кода | десятки модулей и тестов | **минимум: 2–3 hook-скрипта + опц. MCP** |
| Цена в токенах | высокая (рестарты рвут prompt-cache) | **низкая (один прогретый контекст)** |

Материал, который стоило сохранить при этом отказе, перенесён **в этот репозиторий**:
тексты этапов и DoD переписаны в прозу в `skills/volna-flow/stages/*.md`, знание о TFS REST —
в `docs/reference/tfs-rest.md`, рабочий клиент TFS — в `lib/tfs-client.mjs`.
Внешних зависимостей от других проектов у «Волны» нет.

> **Статус этих правил:** они обкатаны примерно на пяти задачах с разным успехом — рабочий
> черновик, а не согласованный командный стандарт. Менять их можно и нужно; уровни
> (`required`/`expected`/`optional`) ставятся осторожно, механизм ревизии встроен в этап
> `capture`.

## Часть 1. Глоссарий

| Термин | Значение |
|---|---|
| **Сессия** | один интерактивный запуск Claude Code. Одна задача ≈ одна сессия (при исчерпании — чек-пойнт + `/clear`). |
| **Этап (Stage)** | шаг предпочтительного флоу (`intake`, `analyze`, …). Имеет вход, DoD и запись в журнал. Не обязателен и не строго упорядочен. |
| **Флоу** | упорядоченный **рекомендованный** список этапов. Разрешены `skip`, `back`, повторные итерации. |
| **Журнал задачи (Task Journal)** | локальный markdown-файл на задачу: что / зачем / почему / как / сделано / осталось / нужно. Append-only по этапам. |
| **Состояние (State)** | минимальный машиночитаемый указатель: активная задача, текущий этап, открытые пункты. |
| **Знание (Knowledge)** | обобщённый, обезличенный от задачи опыт, извлечённый на этапе `capture` и коммитимый в командный репозиторий. |
| **Шапка (Preamble)** | короткий блок контекста, автоматически добавляемый к запросу пользователя hook'ом. |
| **Скилл** | `.claude/skills/<name>/SKILL.md` — инструкция этапа с прогрессивным раскрытием. |
| **Пакет (Plugin)** | распространяемая единица: скиллы + команды + hooks + MCP в одном репозитории. |

## Часть 2. Консолидированные требования

### 2.1. Назначение
Провести разработчика **за руку** от получения задачи в TFS до PR и закрытия, в одном
контексте, сохраняя (а) универсальность обычного чата, (б) воспроизводимость процесса
между разработчиками, (в) накопление журнала и опыта для будущего.

### 2.2. Обязательные возможности
1. **Настройки проекта и процессов — markdown-файлы** в репозитории (git-friendly,
   ревьюабельные, редактируемые вручную).
2. **Мягкий флоу**: этапы как чек-лист с отметками; свободный переход вперёд/назад/через;
   легитимный сценарий «сразу к закрытию — правки кода не потребовались».
3. **Автоматическая подсказка контекста**: к запросу добавляется шапка (активная задача,
   этап, незакрытые пункты, напоминание дописать журнал) — без участия пользователя.
4. **Журнал работ на задачу**: локальный файл, пополняемый **на каждом этапе**; секции
   что / зачем / почему / как / сделано / осталось / нужно.
5. **Автоподъём референса**: по номеру задачи — точно; по смыслу — семантическим поиском
   (похожие прошлые задачи, извлечённые практики).
6. **Работа в указанных репозиториях** напрямую (без worktree), ветка по конвенции.
7. **Полный цикл**: intake → analyze → spec → plan → implement×N → advocate → fixtures →
   unit-tests → visual (человеком) → commit → push → PR → close → capture → next.
8. **Напоминание о новой сессии** по завершении задачи (чек-пойнт → `/clear`).
9. **Расшаривание внутри команды**: один артефакт, устанавливаемый другим разработчиком
   без ручной сборки.
10. **Экономия токенов** как явное требование, а не побочный эффект.

### 2.3. Дополнения, которых не было в исходной формулировке (предлагаются к принятию)
- **D-A. Разделение журнала и знания.** Журнал задачи — сырой и приватный по смыслу;
  Knowledge — обобщённый и командный. Без разделения журналы либо не шарятся, либо тащат
  в командный репозиторий шум. Этап `capture` — мост между ними.
- **D-B. Чек-пойнт по требованию, а не по порогу.** Вместо автоматического сторожа заполнения
  контекста — явная команда `/volna:checkpoint`, плюс `PreCompact`-hook, который гарантирует
  запись журнала до сжатия контекста.
- **D-C. Гейт чистого дерева.** Раз worktree нет, этап `intake` обязан проверять
  `git status` и наличие незакрытой предыдущей задачи. Иначе смешивание задач в одной ветке —
  вопрос времени.
- **D-D. Учёт времени — минимальный.** Штампы начала/конца этапов в журнале; агрегация —
  отдельной командой при закрытии задачи. Полноценный таймшит — вне области.
- **D-E. Пре-коммит гейт вместо доверия.** Требования (стиль тестов/кода/комментариев)
  проверять `PreToolUse`-hook'ом на `git commit`, а не только текстом в промпте.
- **D-F. Индекс журналов — не раньше 20–30 задач.** До этого точного поиска по номеру и
  `Grep` достаточно; вектор без корпуса — преждевременная сложность.

## Часть 3. Противоречия и решения (V1–V10)

**V1. «Можно ли сделать это MCP-сервером?» — Нет, и это не недостаток.**
MCP-сервер принципиально **пассивен**: он предоставляет клиенту tools / resources / prompts
и может запросить у клиента sampling, elicitation, roots. Он **не может**: инжектировать
текст в каждый запрос пользователя, реагировать на события сессии, знать заполнение
контекста, инициировать шаг, запрещать действие. Всё «ведение за руку» лежит вне MCP.
**Решение:** разделить обязанности —
- *ведение флоу* → Skills + slash-команды + **hooks** (единственный механизм автоинъекции);
- *состояние и файлы* → обычные markdown-файлы в репозитории (Read/Write/Edit);
- *интеграции и семантический поиск* → **MCP-сервер** (TFS, индекс журналов/знаний).
MCP в «Волне» — не каркас, а периферия: роль оркестратора берёт на себя человек.

**V2. «Автоматически добавляемые к запросу промпты» — это hooks, конкретно `UserPromptSubmit`.**
Ни CLAUDE.md (статичен), ни skills (вызываются по решению модели), ни MCP prompts
(вызываются пользователем) не дают гарантированной инъекции переменного контекста.
**Решение:** `UserPromptSubmit` возвращает **шапку ≤20 строк**: активная задача, этап k/N,
2–3 незакрытых пункта, одна строка-напоминание. Жёсткий бюджет — иначе шапка × каждое
сообщение съедает больше, чем экономит.

**V3. Мягкость флоу vs гарантии.** Полностью мягкий флоу деградирует до «как получится»;
жёсткий — то, от чего уходим.
**Решение:** трёхуровневая шкала на каждый пункт этапа:
`required` (гейт hook'ом — только для необратимого: commit, push, запись в TFS),
`expected` (напоминание в шапке, пропуск требует одной фразы-обоснования в журнал),
`optional` (только упоминание в скилле). По умолчанию — `expected`.

**V4. Кто хранит состояние.** Дублировать состояние в json и в журнале — рассинхрон.
**Решение:** источник правды — **журнал задачи** (`docs/`-подобный markdown с YAML-frontmatter:
`task`, `stage`, `stages_done[]`, `open[]`). `state.json` — только указатель на активный журнал
(одна строка), пишется теми же командами. Hook читает frontmatter, а не отдельную БД.

**V5. Автоподбор референса: два разных механизма, не один.**
- *точно по номеру* — детерминированно, hook'ом на `SessionStart`/`UserPromptSubmit`:
  regex `\b(\d{4,6})\b` → `journal/TASK-<id>.md` → в шапку;
- *по смыслу* — **по запросу модели**, MCP-tool `volna_recall(query)`. Автоматический
  векторный поиск на каждом сообщении — шум и токены впустую.
**Решение:** оба; автоматический — только точный.

**V6. Свой векторный индекс vs расширение существующего KB-сервера.**
У проекта уже есть работающий MCP-сервер базы знаний (6 инструментов: wiki, code, эталон,
задачи, примеры, кросс-поиск) с готовым пайплайном эмбеддингов.
**Решение:** **расширить его** новым индексом (`journal`, `knowledge`) и одним
инструментом `search_journal`, а не поднимать второй сервер. Дешевле по коду, по токенам
(меньше tool-схем) и по эксплуатации. Отдельный сервер `volna` — только если запись в трекер
понадобится как MCP (см. V7).

**V7. TFS: MCP-tool или CLI-обёртка.**
**Решение:** начать с **CLI-обёртки** (скрипт поверх перенесённого в проект клиента
`lib/tfs-client.mjs`, вызывается через Bash: `volna-tfs get 12345`, `... comment`, `... time`).
Причины: не занимает
tool-схемы в контексте, отлаживается вне Claude, разрешения — обычным правилом на Bash.
Перевести в MCP — только если понадобятся структурированный вывод и `elicitation` для
подтверждений записи. Запись в TFS и создание PR — всегда с подтверждением человека.

**V8. Почему подход с headless-рестартами дорог, и что в «Волне» делать иначе.**
Причины дороговизны — не архитектура сама по себе, а: (а) каждый headless-рестарт заново
оплачивает системный промпт, CLAUDE.md, tool-схемы и заново читает файлы — **prompt-cache
не переиспользуется между процессами**; (б) состояние передаётся текстом через промпт на
каждом шаге; (в) много MCP-серверов → тяжёлые tool-схемы в каждом запросе.
**Решение (бюджет «Волны»):** один долгий контекст (кэш прогрет); шапка ≤20 строк;
`SKILL.md` ≤100 строк с деталями в отдельных файлах, читаемых по необходимости;
инструментов мало и с короткими описаниями (отложенная загрузка схем через ToolSearch —
использовать, а не обходить); KB-поиск вместо чтения больших файлов целиком;
`/compact` после чек-пойнта вместо перезапуска процесса.

**V9. Расшаривание: git-репозиторий с `.claude/` vs плагин.**
Копирование `.claude/` вручную не версионируется и разъезжается между разработчиками.
**Решение:** оформить как **плагин Claude Code** (`.claude-plugin/plugin.json`: skills,
commands, hooks, mcpServers) в отдельном git-репозитории-маркетплейсе. Установка у коллеги —
две команды (`/plugin marketplace add <repo>`, `/plugin install volna`), обновление — `git pull`
маркетплейса. Проектная часть (CLAUDE.md, конвенции репо) остаётся в самом рабочем репозитории.

**V10. Универсальность чата не должна страдать.**
Риск: шапка и скиллы превращают сессию в «только по флоу».
**Решение:** флоу активен только при наличии активной задачи в состоянии; вне задачи шапка
пуста, скиллы молчат. Явная команда `/volna:off` глушит шапку до конца сессии.

## Часть 4. Рекомендованная архитектура

### 4.1. Вердикт
Реализуемо и существенно проще оркестратора. Своего кода — минимум: **три hook-скрипта**
(≈150–250 строк на Node или PowerShell), **набор markdown-скиллов** и **одна CLI-обёртка над
TFS**. MCP — только как расширение уже существующего KB-сервера. Всё остальное — штатные
механизмы Claude Code.

### 4.2. Раскладка (двухчастная)

```
Volna/                             ← публичный репозиторий, он же маркетплейс плагина
  .claude-plugin/
    plugin.json                    ← skills + commands + hooks + (опц.) mcpServers
    marketplace.json               ← чтобы коллега сделал /plugin marketplace add
  install.ps1                      ← установка одной командой PowerShell (без uv/npm)
  .env.example                     ← контракт окружения: адреса, пути, путь к токену
  lib/tfs-client.mjs               ← клиент REST трекера (перенесён в проект)
  skills/
    volna-flow/SKILL.md            ← карта флоу: этапы, DoD, правила skip/back  (≤100 строк)
      stages/intake.md  analyze.md  spec.md  plan.md  implement.md
              advocate.md  fixtures.md  unit-tests.md  visual.md
              commit.md  push-pr.md  close.md  capture.md      ← читаются по необходимости
    volna-journal/SKILL.md         ← формат журнала, шаблон, правила append
  commands/
    init.md  doctor.md  task.md  stage.md  status.md  checkpoint.md
    journal.md  recall.md  skip.md  back.md  close.md  next.md  off.md
  hooks/
    preamble.mjs                   ← UserPromptSubmit: шапка ≤20 строк
    session-start.mjs              ← SessionStart: активная задача + напоминание
    gate.mjs                       ← PreToolUse(Bash: git commit|push): required-пункты
    precompact.mjs                 ← PreCompact: заставить дописать журнал
  bin/
    volna-tfs.mjs                  ← CLI поверх lib/tfs-client.mjs

<рабочий репозиторий>/             ← у каждого свой, журналы здесь
  CLAUDE.md                        ← проектные конвенции (уже есть/дополняется)
  .env                             ← адреса, пути, путь к файлу токена (gitignored)
  .volna/
    state.json                     ← {"active":"TASK-12345","updated":"…"}  (gitignored)
    journal/TASK-12345.md          ← журнал задачи (коммитить или нет — решение команды)
    knowledge/<topic>.md           ← извлечённый опыт (коммитится всегда)
```

### 4.3. Флоу (предпочтительный порядок, 13 этапов)

| # | Этап | Суть | Уровень |
|---|---|---|---|
| 1 | `intake` | взять задачу из TFS, гейт чистого дерева, ветка, создать журнал | required |
| 2 | `analyze` | код + wiki + delphi-эталон + история задач через KB-поиск; похожие задачи через `recall` | expected |
| 3 | `spec` | постановка своими словами, расхождения, вопросы человеку | expected |
| 4 | `plan` | план изменений по файлам, критерии приёмки | expected |
| 5 | `implement` | итерации правок; каждая — запись в журнал | expected |
| 6 | `advocate` | адвокат дьявола: попытка опровергнуть решение | expected |
| 7 | `fixtures` | тестовые данные/эталоны | optional |
| 8 | `unit-tests` | тесты по конвенциям проекта | expected |
| 9 | `visual` | визуальная сверка человеком (скилл `visual-compare` уже есть) | optional |
| 10 | `commit` | гейт required-пунктов, сообщение по конвенции | required |
| 11 | `push-pr` | пуш ветки, PR со ссылкой на задачу | required |
| 12 | `close` | TFS: время, ссылка PR, статус (с подтверждением) | required |
| 13 | `capture` → `next` | обобщить опыт в `knowledge/`, предложить следующую задачу и `/clear` | expected |

Переходы: `/volna:stage <name>` — прыжок куда угодно; `/volna:skip <name> <причина>` —
пропуск с записью в журнал; `/volna:back <name>` — возврат на повторную итерацию (журнал
не переписывается, дописывается новая итерация). Легитимный короткий путь:
`intake → analyze → skip implement → close`.

### 4.4. Ключевые механизмы

- **Шапка (`UserPromptSubmit`)**: читает `state.json` → frontmatter журнала → печатает
  `Задача 12345 «…» · этап 5/13 implement · открыто: 2 пункта · журнал не дописан 12 мин`.
  Бюджет — 20 строк. Пусто, если активной задачи нет.
- **Чек-лист**: штатный трекер задач сессии (TaskCreate/TaskUpdate) заполняется этапами при
  `intake` — пользователь видит прогресс в UI без своего Whiteboard.
- **Журнал (append-only)**: у каждого этапа — своя секция с `## <stage> · <итерация> · <дата>`
  и подпунктами *что / зачем / почему / как / сделано / осталось / нужно*. Повторный заход
  на этап добавляет новую секцию, не трогая прошлую (человекочитаемый event-log вместо
  машинного).
- **Гейт (`PreToolUse`)**: на `git commit`/`git push` проверяет, что required-пункты
  текущего этапа отмечены и журнал не пуст; иначе — блокирует с объяснением. Единственное
  место, где флоу жёсткий.
- **Чек-пойнт**: `/volna:checkpoint` дописывает журнал до состояния «восстановимо с нуля»,
  затем предлагает `/compact` (не рестарт процесса — кэш дороже).
- **Recall**: `/volna:recall <тема>` → `search_journal` KB-сервера по индексу `journal`+`knowledge`.

### 4.5. Что сознательно НЕ делаем
Оркестратор, worktree, параллельные задачи, свой web-UI, RBAC, автоматический сторож контекста
по порогам, вендор-нейтральный слой требований, полноценный таймшит. Каждый пункт здесь —
отвергнутая альтернатива, а не «пока не успели»: они противоречат идее одной сессии и
дешёвого контекста.

## Часть 6. Риски и ограничения (честно)

1. **Один контекст деградирует.** На задачах с большим объёмом чтения качество падает
   раньше, чем кончается окно. Митигация — KB-поиск вместо чтения файлов целиком,
   чек-пойнт + `/compact` по своему ощущению, а не по метрике.
2. **Шапка — это налог.** 20 строк × каждое сообщение. Если пользы не видно — глушить
   `/volna:off`. Пересматривать бюджет после первых 3 задач.
3. **Гейт обходится** руками (`git commit` вне Claude). Это осознанно: «Волна» —
   помощник, не контролёр. Принуждение потребовало бы внешнего процесса — от него мы ушли.
4. **Hooks на Windows хрупки**: пробелы в путях, кодировки, время старта Node. Правило
   «тихий выход 0 при любой ошибке» обязательно, иначе система ломает обычную работу.
5. **Вектор бесполезен на малом корпусе** — не начинать с него (D-F).
6. **Мягкий флоу требует дисциплины.** Если этапы систематически пропускаются без записи —
   это сигнал, что этап лишний, а не что нужен гейт. Пересматривать флоу, а не ужесточать.
