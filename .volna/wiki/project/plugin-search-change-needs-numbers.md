# Правку отбора выбирают числами на живом корпусе, а не читая код

**тип:** направление · **предмет:** правка поиска и её проверка · **этапы:** plan, implement
**раздел:** project

**вывод:** у правки поискового отбора нет наблюдаемого «работает»: и потеря записи, и лишние
находки выглядят одинаково правдоподобно. Поэтому вариант выбирается прототипом в песочнице,
который считает число находок на живом корпусе по набору запросов - включая **заведомо чужие темы**,
где рост находок и есть шум.

Так отпал вариант, казавшийся очевидным при чтении кода: ослабить порог совпадения. По числам он
размывал ответ (7 записей из 36 на запросе из двух слов), и понадобился третий слой - относительный
отсев хвоста.

Второе следствие: **перенос прототипа в код - отдельный источник ошибок**. Из трёх условий
прототипа в правку попало два, и прогон по критериям приёмки поймал это сразу (0 находок вместо
замеренных 4). Критерий приёмки, записанный числом, тут отличает «стало лучше» от «стало хуже»;
записанный словами - не отличает.
