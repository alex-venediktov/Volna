# Настройки проекта для «Волны»

> Копия этого файла живёт как `.volna/project.md` в рабочем репозитории и **коммитится** —
> это общая для команды часть настроек: команды и конвенции, без секретов и без машинных путей.
>
> Всё приватное — адреса, пути, PAT — берётся из `.env` рабочего репозитория и здесь
> упоминается только именем переменной. Заполнить `.env` по `.env.example` («Волна»),
> проверить — `/volna:doctor`.

## Профиль

Чем этот проект отличается от соседнего: что в нём есть, а чего нет. Этапы читают эти строки
первым делом и **не делают того, чего в проекте нет**. Отсутствующий шаг — не пропуск этапа:
причина в журнал не пишется, `/volna:doctor` о нём не напоминает, вопрос человеку не задаётся.

- репозитории: <один|несколько>          # один = каталог с .volna; несколько = таблица ниже
- трекер: <нет|tfs>
- приём задач: <текст|номер|оба>         # при «трекер: нет» — только текст
- доставка: <commit|commit+push|commit+push+pr>
- закрытие: <журнал|трекер>              # при «трекер: нет» — только журнал
- эталон: <нет|delphi>

**Угловые скобки — это незаполненное поле, а не значение.** Оставленный плейсхолдер этапы
читают как «человек ещё не ответил»: `intake` остановится и спросит, `/volna:doctor` покажет
строку красным. Так и задумано — молча работать по угаданному профилю хуже, чем задать вопрос.
Заполнить вопросами: `/volna:init` (он же спросит по одной строке и запишет ответы).

Имена ключей и значений менять нельзя: по ним профиль читают этапы и hooks (`readProfile`).
Строки нет **вовсе** (файл заведён до появления профиля) → берётся прежнее поведение «Волны»:
несколько репозиториев, трекер `tfs`, приём по номеру, полная доставка, закрытие в трекере,
эталон Delphi. Отсутствие строки и незаполненная строка — разные вещи: первое означает старый
проект, который работает как работал, второе — новый, у которого ещё не спросили.

Типовые наборы: продуктовая команда с трекером — `несколько · tfs · номер · commit+push+pr ·
трекер · delphi`; свой репозиторий без трекера — `один · нет · текст · commit+push · журнал ·
нет`.

Что меняет каждая заполненная строка:

| Строка | Значение | Что происходит |
|---|---|---|
| `репозитории` | `один` | работа в каталоге с `.volna`, `repos[]` журнала пуст, таблица ниже не нужна |
| `трекер` | `нет` | все задачи локальные (`mode: local`): `plan` не ставит статус, задача-фикс и PR не создаются, гейт не блокирует push |
| `приём задач` | `текст` | `/volna:task` принимает текст или файл; число тоже читается как локальный id, а не как номер в трекере |
| `доставка` | `commit+push` | `deliver` = коммит и push; PR не создаётся |
| `закрытие` | `журнал` | `close` идёт ветвью Г: часы и итог в журнал, статусы двигать негде |
| `эталон` | `нет` | `analyze`, `plan` и `implement` работают без сверки с эталонной реализацией, правила порта не применяются |

## Репозитории

Профиль `репозитории: один` → таблицу заполнять не надо: правки идут в репозиторий, где лежит
`.volna`, и путь к нему знать неоткуда не нужно.

Профиль `репозитории: несколько` → перечислить роли. Имя переменной выбирает проект
(`REPO_MAIN`, `REPO_UI`, `REPO_DOCS` — любое, лишь бы начиналось с `REPO_`), значение — путь —
лежит в `.env`:

| Имя | Переменная | Что там |
|---|---|---|
| `<имя роли>` | `REPO_<ИМЯ>` | `<что там>` |

Незаполненная переменная = репозиторий в работе не участвует. Имена из первой колонки — это то,
что этапы пишут в `repos[]` журнала задачи.

## Эталон

Действует при `эталон: delphi`; при `эталон: нет` раздел не нужен целиком.

- корень исходников эталона — `REF_ROOT` (прежнее имя `DELPHI_REF_ROOT` тоже читается);
- ключевой модуль, куда смотреть первым — `REF_MAIN`;
- каталог эталонных скриншотов для этапа `visual` — `<заполнить>`;
- эталоны непиксельных выходов (ожидаемые печатные формы, выгрузки, наборы сообщений) —
  `<заполнить или убрать строку>`;
- **версия эталона критична**: сверяться только с той, что указана командой. Открытая по
  ошибке другая версия — типовая причина «значения не сходятся».

## Трекер задач

Действует при `трекер: tfs`; при `трекер: нет` раздел не нужен целиком.

- база — `TFS_BASE_URL`, проект — `TFS_PROJECT`, область команды — `TFS_AREA_PATH`;
- доступ — PAT из файла `TFS_PAT_FILE` (utf-8-sig, края обрезаются). Секрет в переменную
  окружения не кладём;
- **статусы двигает** — `слияние PR` | `закрывающий вручную` (`<заполнить>`). От этого зависит
  ветка А этапа `close`: там, где статусы двигает слияние, задача-фикс закрывается сама, а этап
  сводится к списанию времени, остатку и маршруту;
- **исполнитель новой задачи** — текущий пользователь (`volna-tfs whoami` показывает, кто это);
  другой ставится флагом `--assign` осознанно;
- обязательные поля процесса у новых задач — `volna-tfs fields <тип>` показывает их и допустимые
  значения, `--field ref=значение` задаёт, `--like <id>` снимает с соседней задачи области. Без
  них сервер отвечает `TF401320`. Постоянное значение области — **запись в `.volna/knowledge/tfs/`**
  (секция `deliver` указателя), не переменная окружения: это знание о процессе, а не настройка
  машины;
- многострочные поля (описание, комментарий) принимают **Markdown** — HTML собирает обёртка и
  вход экранирует, поэтому написанные руками теги видны в трекере текстом;
- подвохи REST API (кодировка тела, `$expand=relations`, HTML в многострочных полях) —
  `docs/reference/tfs-rest.md` «Волны»; готовый клиент — `lib/tfs-client.mjs`.

## База знаний

MCP-сервер поиска по коду, эталону, wiki и обсуждениям: имя — `KB_MCP_NAME`, инструменты
`search_delphi`, `search_code`, `search_wiki`, `search_tasks`, `search_samples`.
Сервер не настроен или недоступен → искать `Grep`/`Glob` и отмечать это в журнале.

Индекс не обновляется сам: после слияния изменений его переиндексируют командой из раздела
«Команды». Строка не заполнена → этап `close` пропускает реиндексацию и говорит об этом.

## Конвенции

- ветка: `bugfix/<id>-<slug>` для bug, `feature/<id>-<slug>` для story/task; целевая ветка
  для PR и для отвода новых — `TARGET_BRANCH` (прежнее имя `TFS_TARGET_BRANCH` тоже читается);
- коммит: одна строка `<id> <что сделано>`; `git add -A` перед коммитом; **без** трейлеров
  (в том числе без `Co-Authored-By`). Префикс бывает двух видов, и стоит назвать оба: **задачный**
  (`<id задачи или номер в трекере>`) — обычный случай; **версионный** (`версия <X.Y.Z>`) — если
  проект выпускается версиями и правка её меняет. Правка, версию не меняющая, идёт с задачным
  префиксом даже в версионном проекте;
- комментарии: одна строка «что делает (`<источник>`)», русский язык,
  ASCII-пунктуация (`->`, `-`, `"`), без номеров задач;
- тесты: PascalCase `Method_State_Expected`, обязательный `/// <summary>`;
- фикстуры: оффлайн-снимок данных в JSON, без обращения к живой БД.

Если в репозитории есть свои скиллы под эти конвенции (стиль комментариев, сообщение коммита,
стиль тестов, порт эталона) — этапы «Волны» используют их; карта соответствия —
`docs/PROJECT-SKILLS.md`.

## Локальное (не коммитить)

Машинно-зависимое — в `.env`; всё, что нужно вынести из этого файла персонально, —
в `.volna/project.local.md` (уже в `.gitignore`).
