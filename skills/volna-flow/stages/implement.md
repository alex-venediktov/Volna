# Этап 5 · implement — реализация · expected

Итеративный этап: заходов может быть несколько, каждый — своя секция в журнале. **Любая
доработка кода — это тоже `implement`**, новая итерация, а не «мелкая правка на другом этапе»
(см. «Доработки»).

## Перед первой итерацией
1. **Знания по теме.** Секция `implement` в `.volna/knowledge/INDEX.md`: открыть записи,
   относящиеся к предмету задачи (грабли порта, особенности эталона). Каталог целиком не читать.
   Сказать человеку одной строкой, какие записи открыты и что из них применяем.
2. **Гейт рабочего дерева.** `git status` в каждом затронутом репозитории. Есть незакоммиченные
   изменения → остановиться и спросить человека, что с ними делать. Worktree на задачу в «Волне»
   нет, поэтому это единственная защита от смешивания задач.
3. **Создать ветку** по конвенции из `.volna/project.md`: `bugfix/<id>-<slug>` для bug,
   `feature/<id>-<slug>` для story/task. Ветка отводится от актуального состояния целевой ветки
   (уточнить у человека, если не очевидно) — во всех затронутых репозиториях.
4. Записать в журнал ветку — до первой правки кода. Задача в трекере всё ещё не `Active` (этап
   `plan` пропущен) → поставить статус сейчас, командой из `stages/plan.md`.

## Правила порта Delphi → .NET
1. **1:1 с эталоном.** Логика портируется построчно-эквивалентно. Каждый нетривиальный расчёт
   получает ссылку `(<модуль>.pas:NNNN)`.
2. **Никаких эвристик.** Запрещено вводить сглаживания, скругления, «улучшения» и подобранные
   коэффициенты, которых нет в оригинале.
3. **Паритет имён и значений.** Имена переменных/констант и числа (допуски, смещения,
   коэффициенты) — как в Delphi. Не переименовывать, не «нормализовать».
4. **Никакой реконструкции по результату.** Код выводится из формулы Delphi, а не подгоняется
   под эталонный PNG. Картинка — только для проверки (этап `visual`), не для вывода формулы.
5. **Полнота.** Метод портируется целиком, со всеми ветвями и режимами, а не только той,
   что видна в постановке.

## Комментарии
Одна строка формата «что делает (`<модуль>.pas:NNNN`)». Без многострочных блоков, без
номеров задач и тикетов. Язык — русский без жаргона («признак», а не «флаг»; «условие», а не
«гейт»), пунктуация — только ASCII (`->`, `-`, прямые кавычки).

Правила касаются **только добавленных и изменённых строк**. Существующие легаси-комментарии
массово не переписываем.

## Ход работы
- Правки — минимальным диффом по плану; посторонние улучшения в ту же задачу не тащим.
- После каждой осмысленной итерации: сборка/тесты командами из `.volna/project.md`.
- Сработал СТОП-критерий (значение не сходится, ветви нет в эталоне, постановка
  двусмысленна) → **остановиться и спросить**. Подставить своё значение и закоммитить — прямой
  путь к тихому дефекту.
- Правок кода не потребовалось → этап пропускается: причина строкой в журнал и сразу `/volna:close`,
  минуя гейт выше. Пустой коммит недопустим.

## Доработки
Правка кода после того, как этап один раз закрыт — находки `advocate`, красные тесты, вердикт
человека на `visual`, замечания в PR — это **новая итерация `implement`** (`/volna:implement`)
со своей секцией журнала. Гейт «перед первой итерацией» уже
пройден, а вот **`advocate` после итерации обязателен снова** — на полном `git diff`: правка,
сделанная в ответ на находку, сама может ломать ветвь или эквивалентность эталону.

Цикл `implement → advocate` повторяется, пока адвокат не даст «чисто».

## DoD
Код собирается, изменения соответствуют плану и правилам порта, ссылки на эталон стоят,
ветка создана, незакрытые вопросы — в `open[]`.

## В журнал
Секция `implement · итерация N`: что изменено (файлы), почему выбран такой вариант, ссылки на
строки Delphi, результат сборки/тестов, что осталось. Итерация 1 дополнительно — ветка и
применённые записи knowledge. Итерация N+1 — причина возврата (чья находка).

## Типичные ошибки
- Подгон значения «чтобы совпало» вместо остановки и вопроса.
- Порт только той ветви, которая видна в баге.
- Комментарий с номером задачи вместо ссылки на строку эталона.
- Доработка мимо `advocate` — «там же две строки».
