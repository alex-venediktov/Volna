# Этап 10 · deliver — доставка: коммит, задача-фикс, push, PR · required

Единый гейт доставки: с коммита и до PR. Всё, что здесь делается, необратимо или видно другим
людям — только по явному «да». **«Да» одно на весь этап**: человек решает «доставляем», а не
отвечает трижды на коммит, push и PR по отдельности.

Автопроходом в этап не входят: цепочка `intake` → `visual` кончается перед ним.

Знание по этапу — секция `deliver` указателя `.volna/knowledge/INDEX.md` (как на `plan` и
`implement`): поля процесса трекера, конвенции PR, грабли записи накапливаются там. Секции нет
или она пуста — не ошибка, идём дальше.

## Порядок (для bug важен именно такой)
1. **Показать человеку дифф** и спросить решение: доставляем (коммит → push → PR) или изменений
   кода нет (PR не создаём, идём на `close`). Среди вариантов — «вернусь и посмотрю».
2. **Открыть секцию журнала по этапу до `git commit`.** Гейт `gate.mjs` отказывает в коммите,
   пока в журнале нет секции по текущему `stage`; и это не формальность — после коммита контекст
   уходит, а «почему так» остаётся только в журнале.
3. **Коммит** — правила ниже.
4. **Создать задачу-фикс в TFS** — до push, чтобы в PR стоял её номер, а не номер бага:
   - описание **краткое**: суть правки в 1–2 предложениях, без простыней;
   - описание — **Markdown**: абзацы, списки `-` и `1.`, заголовки `#`, `**жирный**`, код,
     ссылки. HTML собирает обёртка, вход она экранирует, поэтому поданные теги видны в трекере
     текстом. Уже записанное чинится `describe --replace`;
   - эстимация и привязка к багу (родитель/related);
   - **исполнитель** — текущий пользователь по умолчанию, другой ставится `--assign` осознанно.
     Ответ команды печатает исполнителя и состояние: сверить их **сразу**. Потом не выйдет —
     в поле уже будет стоять исправленное человеком значение, и оно выглядит как исходное;
   - обязательные поля процесса — `fields <тип>` до создания, значение с соседней задачи
     области — `--like <id>`;
   - рекламация → сослаться на прежнюю задачу-фикс и её PR;
   - id задачи-фикса → в `fix_task` frontmatter журнала.
5. **Push ветки.**
6. **Создать PR**: заголовок со ссылкой на задачу-фикс, краткое описание правки, ссылка на
   строки эталона Delphi. Приложить артефакт сверки, если он есть (этап `visual`: склейка,
   PDF, собранная форма, лог прогона); если получить его нельзя — явно указать причину.

## Коммит

Перед ним: пройден `advocate` (или человек сознательно его пропустил), тесты прогнаны и вывод в
журнале, последняя итерация `implement` записана, `git status` просмотрен — понятно, что уходит.

1. **`git add -A`** — все изменения, включая **новые (untracked)** файлы. Новые тесты и классы
   обязаны попасть в коммит, иначе они не дойдут до PR. Наблюдался «успешный» коммит без новых
   файлов — проверять обязательно.
2. Сообщение — **одна строка**: `<id-воркайтема> <что сделано>`.
   - номер бага, пока задача-фикс не создана (она появляется шагом позже); если фикс уже
     создан — её номер;
   - запрещены: слово «golden», многострочные тела, **любые трейлеры, включая
     `Co-Authored-By`** (это правило проекта; оно переопределяет общие настройки).
3. После коммита проверить: `git status` — дерево чистое, untracked не осталось; `git log -1` —
   HEAD продвинулся, коммит непустой.

```
git add -A
git commit -m "21571 порт условия видимости клапана при зеркале"
```

Сообщение — по скиллу `volna-craft:commit-style`, если он установлен.

## Команды CLI

```
volna-tfs create Task --title "<суть>" --parent <id бага> --estimate <часы> \
                    [--tags A,B] [--body-file <файл>] [--field <ref>=<значение>] \
                    [--like <id соседней задачи>] [--assign <кто>]               задача-фикс
volna-tfs fields <тип>                      обязательные поля процесса и их значения
volna-tfs whoami                            кто будет исполнителем по умолчанию
volna-tfs pr list <репо> --source <ветка>   не создан ли PR на эту ветку раньше
volna-tfs pr create <репо> <ветка> --title "<номер>: суть" --body-file <файл> \
                    [--target <ветка>] [--work-item <номер>]
volna-tfs pr status <репо> <номер>          состояние: слияние, коммиты
volna-tfs link-pr <id> <репо> <номер>       связь задача-PR, если PR уже создан
volna-tfs link <id> <цель> [--rel related|duplicate]   связь между задачами
```

- флага подтверждения у команд нет: решение о необратимом даёт человек в разговоре, а
  `--dry-run` печатает, что уйдёт в трекер, ничего не отправляя;
- **описание — файлом** (`--body-file`), не аргументом: длинный текст с кириллицей в командной
  строке бьётся, а файл читается как UTF8. Содержимое файла — Markdown;
- `create` без `--estimate` заводит задачу без часов и об этом предупреждает: по конвенции
  команды оценка и остаток у новой задачи равны и заполняются сразу;
- процесс трекера может требовать полей, которых нет среди флагов (контроль проекта, приоритет):
  посмотреть их заранее — `fields <тип>`, снять значение с соседней задачи области — `--like <id>`.
  На отказе `TF401320` команда сама печатает поле, допустимые значения процесса и то, что стоит в
  этом поле у родителя, но не подставляет молча. Значение постоянно для области — его место
  **знание** (`.volna/knowledge/tfs/`, секция `deliver` указателя), а не переменная окружения.
  Собирать запрос вручную в обход CLI не надо;
- `--work-item` ставит нативную связь сразу — без неё трассировка задача-PR теряется;
- целевая ветка: `--target` или `TFS_TARGET_BRANCH` в `.env`. Угадывать её команда не будет;
- после создания посмотреть `mergeStatus`: `conflicts` — PR слить нельзя, говорить «готово» рано;
- **несколько коммитов в PR** = ветка отведена не от целевой, а от другой feature-ветки. Тогда
  порядок слияния важен, и его надо назвать человеку явно.

## Изменений кода нет
Пустой или фиктивный коммит не делается, PR не создаётся. Явно сказать «изменений кода нет» и
идти на `close` (ветка «закрыть без PR»).

## Для story
Задача-фикс не создаётся. Если работа была в коде — обычный PR со ссылкой на US.

## Для локальной задачи (`mode: local`)
Задачи-фикса и PR нет: создавать их не в чем. Этап сводится к одному из двух:

- **есть что зафиксировать** (код, скрипт, запись в `knowledge/`, документ) → коммит по правилам
  выше, с той разницей, что в сообщении вместо номера воркайтема — id задачи (`260730-<slug>`).
  Push — по решению человека, гейт его в этом режиме не блокирует; ветка нужна, только если она
  создавалась на `implement`;
- **фиксировать нечего** (разбор кончился выводом в журнале) → пропуск этапа строкой причины
  в журнал, дальше `close`. Пустой коммит недопустим и здесь.

Решение «доставляем или нечего» — то же одно «да» человека, что и в трекерном режиме: этап
`required` не потому, что трогает трекер, а потому, что коммит и push видны другим людям.

## Что НЕ делать здесь
- Не писать в сам баг пространных отчётов «что и зачем сделано» — там место кратчайшему
  описанию и скриншоту (этап `close`).
- Не создавать подзадачи на других исполнителей: это **отдельное** предложение человеку, не
  смешивать с доставкой.
- Не менять статусы work item'ов — это `close`.

## DoD
Коммит существует и содержит все изменения (дерево чистое, untracked нет), сообщение по
конвенции; задача-фикс создана (для bug); ветка запушена; PR создан. Хеш коммита, id задачи-фикса
и ссылка на PR записаны в журнал.

## Типичные ошибки
- `git commit -am` — новые файлы не попадут.
- Многострочное сообщение коммита или трейлер.
- Коммит без разрешения человека.
- Push до создания задачи-фикса → в PR номер бага, трассировка теряется.
- **HTML руками** в описание work item → теги видны в тексте постановки: вход `create` и
  `describe` — Markdown. Исправляется повторной записью `describe --replace`.
- Задача-фикс без исполнителя или на чужом человеке: проверять по печати команды, а не по полю
  в трекере после ручной правки.
- Длинный комментарий в самом баге.
