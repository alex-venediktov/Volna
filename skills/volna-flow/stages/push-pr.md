# Этап 11 · push-pr — задача-фикс, push, PR · required

Единый гейт доставки. Всё, что здесь делается, видно другим людям — только по явному «да».

## Порядок (для bug важен именно такой)
1. **Показать человеку дифф** и спросить решение: `push` (есть фикс) или `close` (изменений
   кода нет → PR не создаём, идём на `close`).
2. **Создать задачу-фикс в TFS** — до push, чтобы в PR стоял её номер, а не номер бага:
   - описание **краткое**: суть правки в 1–2 предложениях, без простыней;
   - эстимация и привязка к багу (родитель/related);
   - рекламация → сослаться на прежнюю задачу-фикс и её PR;
   - многострочный текст перед записью превратить в HTML (`<p>`, `<ul><li>`, `<pre><code>`),
     спецсимволы экранировать: on-prem TFS не рендерит Markdown;
   - id задачи-фикса → в `fix_task` frontmatter журнала.
3. **Push ветки.**
4. **Создать PR**: заголовок со ссылкой на задачу-фикс, краткое описание правки, ссылка на
   строки эталона Delphi. Приложить скриншот исправления, если он есть (этап `visual`); если
   получить его нельзя — явно указать причину.

## Для story
Задача-фикс не создаётся. Если работа была в коде — обычный PR со ссылкой на US.

## Что НЕ делать здесь
- Не писать в сам баг пространных отчётов «что и зачем сделано» — там место кратчайшему
  описанию и скриншоту (этап `close`).
- Не создавать подзадачи на других исполнителей: это **отдельное** предложение человеку, не
  смешивать с доставкой.
- Не менять статусы work item'ов — это `close`.

## DoD
Задача-фикс создана (для bug), ветка запушена, PR создан и его ссылка вместе с id задачи-фикса
записаны в журнал.

## Типичные ошибки
- Push до создания задачи-фикса → в PR номер бага, трассировка теряется.
- Markdown в описание work item → в TFS отображается кашей.
- Длинный комментарий в самом баге.
