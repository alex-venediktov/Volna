# Задача из нескольких частей

Правило коротко — в `SKILL.md`, раздел «Задача из нескольких частей». Здесь механика целиком: она
нужна, только когда работа не помещается в один заход, и тело скилла ею платить не должно.

## Что это и чем не является

Крупная работа остаётся **одной задачей с одним журналом**. Части — это её внутреннее деление:
цикл `spec` → `plan` → `implement` ⇄ `advocate` → тесты → `capture` → `deliver` → `close`
повторяется по разу на каждую часть, а между частями стоит `/clear`.

Отдельных задач на части не заводится, отдельного файла плана не появляется. Всё, что нужно для
продолжения, живёт там же, где и всегда: **список частей — в подпункте `**части:**` секции
`## Состояние`**, история заходов — в логе итераций, номер текущей части — в `part`/`parts`
frontmatter. Механизм повторного захода на этап тоже не новый: повторный вызов этапа **уже**
открывает новую итерацию, и части им и пользуются.

Активная задача при этом одна, как и была: `state.json` через `/clear` продолжает указывать на
неё. Побочный плюс — гейт на коммит работает всю дорогу, а не выключается после первой части.

## Когда предлагать деление

Признак — на `analyze` видно **несколько независимых результатов**, каждый со своим «готово,
когда»: правки в разных слоях, не связанные общим диффом; работа, где второй кусок начинается
только после того, как первый доехал; оценка, которая не влезает в один заход контекста.

Решает **человек**, `spec` только предлагает вариантами: вести одной задачей или разбить.
Догадкой тип работы не выбирается — деление меняет порядок работы на дни вперёд.

Согласились — записать:

```
**части:**
1. схема хранения - сделано (2026-08-16, 3ч)
2. приём шага по форме - в работе
3. продолжение цепочки - не начата
```

и во frontmatter `part: 2`, `parts: 3`. Состояния части: `не начата` · `в работе` · `сделано`
(с датой и часами) · `снята` (с причиной). Постановка части — там же, одной строкой; не
помещается в строку — абзац под пунктом, но не отдельный документ: разросшийся список частей
значит, что это были разные задачи, а не части одной.

Число частей — оценка, а не обязательство: часть можно снять, добавить или слить с соседней.
Изменилось — переписать список и поправить `parts`.

## Что меняется на этапах

| Этап | Часть закрыта, остаток есть |
|---|---|
| `spec` | своя итерация на каждую часть: постановка **этой** части и её критерии приёмки |
| `plan` | план по файлам — только для текущей части |
| `deliver` | коммит части; сообщение называет часть (`<id> часть 2: приём шага по форме`) |
| `close` | итог **части**, часы части — в журнал; в трекер не списываем, статус задачи не закрываем |
| `cleanup` | уборка без завершения: активная задача **не снимается**, ветка задачи **не удаляется** |

Всё остальное — как обычно: `advocate` после каждой итерации, тесты, `capture` до коммита.

**Коммит на часть — норма, но не обязанность.** Держать несколько частей в одном коммите законно,
если человек так решил: деление на части про порядок работы, а не про историю репозитория.
Ветка — одна на задачу, части ложатся в неё подряд; PR (там, где он есть) один и дополняется.

**Часы копятся, а списываются один раз.** `close` части считает её время и пишет в журнал; в
трекер уходит **сумма**, на полном закрытии. Иначе задача под списание заводится по разу на часть,
а в отчётах команды работа рассыпается.

## Продолжение после `/clear`

`/volna:task` **без аргумента**: есть активная задача с остатком (в списке частей остались
незакрытые) — поднять её, показать карточку с остатком и идти в `spec` следующей части,
не спрашивая «начинаем?». Это и есть последняя строка хода у `cleanup` части:
команда без аргумента, её принимает `Tab`.

Активной задачи нет или остатка нет — прежнее поведение: спросить, ничего не предполагая.

## Полное закрытие

Последняя часть сделана — `close` идёт обычным порядком: итог всей задачи, **суммарные** часы,
статусы в трекере. Дальше `cleanup` завершает работу как всегда: активная задача снимается, ветка
удаляется по общим правилам, последняя строка — `/clear`.

Работа брошена на середине (передумали, приоритет ушёл) — это тоже полное закрытие: незакрытые
части перечисляются в итоге и в `open[]`, состояние `снята` с причиной. Задача, оставленная
активной «на потом», блокирует следующую и через неделю выглядит как забытая.
