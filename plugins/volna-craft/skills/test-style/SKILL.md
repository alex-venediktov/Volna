# Оформление тестов

Правила обязательны для любого нового теста и тест-фикстуры. Конкретный фреймворк, регистр
имён и настройки сборки — в `.volna/project.md`; здесь то, что не зависит от стека.

## 1. Имя говорит о поведении

Имя тест-метода — утверждение о проверяемом поведении, а не «тест метода X».
Имя класса-фикстуры — `<Субъект>Tests` (или конвенция проекта).

```csharp
[TestFixture]
public class SupportSideHandlerTests
{
    [Test]
    public void DetectsSupportSideFromDirectionField() { ... }
}
```

- метод — глагол или утверждение: `ReturnsEmptyWhenNoCoating`, `MirrorsLeftViewForBentUnit`;
- фигурирует конкретный набор данных — допустим хвостом: `Diagnose106608GeneralViewMeasures`;
- регистр (PascalCase, snake_case) — по конвенции проекта, **единообразно** в файле.

## 2. Слова в именах и описаниях

- **Не использовать жаргон** в именах классов, методов, файлов эталонов и папок. Эталонный
  снимок называть нейтрально (`Reference`, «эталон»), файлы — по сути содержимого.
- **Избегать американизмов**, где есть нейтральный аналог.
- **Описание — самое краткое**, одной фразой по сути проверки, без преамбул.
- **Не описывать прежнее или неверное поведение** — только корректное целевое плюс ссылка на
  эталон (правила текста — скилл `code-comments`).

## 3. Doc-комментарий обязателен

Над каждым тест-методом и над классом-фикстурой — короткий doc-комментарий: **что проверяем и
при каком условии**.

```csharp
/// <summary>Опорная сторона определяется по полю направления, когда автоопределение выключено.</summary>
[Test]
public void DetectsSupportSideFromDirectionField() { ... }
```

Это жёсткое требование, а не пожелание: при `TreatWarningsAsErrors` или генерации документации
отсутствующий doc-комментарий даёт предупреждение сборки (в .NET — `CS1591`). Таких
предупреждений по добавленным и изменённым тестам быть не должно — проверять до коммита.

## 4. Что коммитим

- **Подтверждённый факт → тест с эталонным значением**, офлайн, на фикстуре (скилл
  `test-fixtures`).
- **Одноразовые диагностические леса и дампы не коммитим.** Помеченный `[Explicit]` (или
  аналогом) харнес, который читает живую БД или пишет файлы, — временный: воссоздаём, снимаем
  нужное, удаляем. Его код держим в скилле или в материалах проекта, а не в ветке.
- **Тест без живой БД и сети.** Живой доступ делает тест недетерминированным и привязывает
  прогон к VPN и данным.

## Чек-лист перед коммитом теста

- [ ] Имя класса и метода читаются как утверждение о поведении, регистр — по конвенции проекта.
- [ ] Есть doc-комментарий с условием и ожиданием; предупреждений сборки по нему нет.
- [ ] Нет жаргона в именах и файлах эталонов.
- [ ] Диагностические леса не попали в коммит.
- [ ] Тест детерминирован: фикстура вместо живой БД, если это не явный live-кейс.
- [ ] Для багфикса: тест **падал бы до правки** — иначе он не доказывает исправление.
